# Accessibility Audit — Form Controls + Cross-Cutting — 2026-08-13

Scope: the `Edit*` form controls, their shared label/validation/shell infrastructure, `edit-controls.css`,
the `Select<T>` engine, the date subsystem and its seam onto the UI-kit pickers, plus a runtime pass over
the whole library. Audited against WCAG 2.2 AA and the WAI-ARIA Authoring Practices (APG).

The UI kit was audited separately on 2026-08-11 (`UIKIT-A11Y-AUDIT-2026-08-11.md`); **the form controls had
never been audited**. That was the gap this pass targeted.

## Method

Nine independent angles run in parallel, then cross-checked against each other and against a live browser:

- Six source audits by subsystem (select engine, date, text/number, radio/bool, checked-lists/file/display,
  labeling+validation infrastructure) and one stylesheet audit.
- One test-coverage analysis (what the suite asserts vs. what can regress silently).
- One regression check of the 2026-08-11 remediation.
- A runtime **axe-core 4.10.2** pass over `/` and `/uikit` on the live Debug host, at rest *and* with
  dropdowns/pickers open, plus hand-computed contrast and target-size measurement.

Findings that source-reading and the browser disagreed on were resolved in favour of the browser.
Several candidate findings were **killed** by measurement (see *Verified non-issues*) — that list is part of
the deliverable, because it prevents wasted remediation effort.

## The headline: why all of this shipped with a green test suite

This is the single most important result, because it explains every other finding and is the only one whose
fix prevents recurrence.

**The e2e suite has essentially no accessibility-tree coverage of the controls it tests.** Measured:

| Locator style | Count |
|---|---|
| `Locator(...)` — CSS/class/id | **831** |
| `GetByRole(...)` | **20** |
| `GetByLabel(...)` | **0** |

All 20 `GetByRole` calls are `AriaRole.Button`, and every one targets demo-scaffold chrome ("Submit",
"Edit Mode", "Display bound values") — **never the input, select, or combobox under test**. CSS locators
resolve regardless of whether the accessibility tree is intact, so the suite's green status carries no
correlation with whether a control is reachable by role or name.

There is also **no axe-core integration** (`grep` for `axe`/`Deque`/`AxeBuilder` → zero hits), and the
visual-regression baselines are diff-only: they compare against whatever PNG is checked in, with no notion
of "this colour fails WCAG". Both contrast defects below are *already baked into committed baselines*, so
that tool will pass on them indefinitely. No baseline captures a focused state at all (none of the 36 PNGs
has "focus" in its name), so a removed focus ring has no visual surface either.

Consequence: a combobox with **no accessible name** and an `aria-expanded` on an element whose role forbids
it both shipped through a fully passing suite. Neither is an exotic bug; both are what an automated scanner
finds in seconds.

**Recommendation (highest leverage in this document):** add `Deque.AxeCore.Playwright` at the
`PageTestBase.NavigateAsync` hook (`PageTestBase.cs:57-71`) — the one method every per-control e2e class
already calls after hydration. Given the pre-existing violation count, gate it with a checked-in allow-list
that fails only on *new* violations, mirroring the ratchet `VisualRegression.cs` already uses for baselines.

## Cross-cutting root causes

These recurred across subsystems that were audited independently and blind to each other — which is the
strongest signal in the audit, since no single reviewer could have seen the pattern.

### A. Focus dropped to `<body>` when an element unmounts — 5 sites
The library already knows this failure mode and solved it twice (`JsInteropEc.FocusById` for `EditFile`;
`PickerDisabledDayKeyboardE2ETests` exists *because* of a prior focus-stranding bug). It was not applied at:
`HidingMode` unmounting a focused input (TXT-1), the picker Clear button (DTE-2), the Select outside-click
backdrop (SEL-8), `RadioOtherInput` being disabled under a focused cursor (RAD-8), and `EditFile`'s
remove-file re-render (untested — coverage gap #4).

### B. One mis-specified colour token, not several contrast bugs
`--wss-color-text-secondary` / `--edit-color-text-secondary` is `rgba(0,0,0,0.45)`, which composites over
white to `#8c8c8c` = **3.36:1**. The library's own comment (`edit-controls.css:1325`) documents it as
"~4.1:1", so the decision to accept it for text was made against a number too generous by ~0.75.
The same comment block calls `rgba(0,0,0,0.55)` "~6.5:1"; it is **4.76:1**. Both errors run the same
direction. Verified two independent ways (axe measurement + hand-computed relative luminance).

This single token accounts for the picker weekday headers (3.36:1), `.edit-file-formats` (3.03:1 on its
`#f3f3f3` zone), and `.edit-file-size`. Separately, `edit-controls.css` *did* remediate its placeholder
token with an explicit WCAG comment, but `wss-controls.css:54` still ships
`--wss-color-placeholder: #bfbfbf` at **1.84:1** — the form stylesheet got the fix, the kit stylesheet
didn't.

**Careful: two distinct tokens both render as `#bfbfbf`, so one fix will not cover both.** The table
empty-state ("No rows match your filter", measured 1.83:1) does *not* use the placeholder token — it uses
`--wss-color-text-disabled: rgba(0,0,0,0.25)` (`wss-controls.css:2156-2159`), which composites to the same
`#bfbfbf`. That token is legitimately disabled-grade and exempt under 1.4.3 *for disabled controls* — but
this is ordinary content text, and it is the only feedback that a filter matched nothing, so the exemption
does not apply here. Fixing `--wss-color-placeholder` alone would leave the table untouched.

### C. Generic accessible names on repeated affordances — 4 subsystems
"Clear", "Show password", "More information", "Choose date", "Custom text value input" are fixed literals
with no field context. On any real form with two of the same control, a screen-reader user browsing by
button list hears the same name repeated with no way to tell them apart.
(TXT-4, INF-6, DTE-7, RAD-4.)

### D. Duplicate DOM ids for repeated control instances
Found independently by two agents (INF-2, TXT-3). `GetId` derives the id from the field name alone;
disambiguation via `IdPrefix`/`FormGroupOptions` is entirely opt-in and silent when skipped. In a
`@foreach` row editor, every instance past the first mislabels: `label[for]` and `aria-describedby` both
resolve through `getElementById`, which returns only the first match.

## Priority 2

6. **Out-of-range typed dates are rejected silently** — no error, no announcement, no validation message;
   `CommitTextAsync` returns `false` without invoking `OnParseError`. The value simply reverts.
   (`DatePicker.razor.cs:1252-1274`, `DateRangePicker.razor.cs:1569-1636`) — WCAG 3.3.1.
7. **`HidingMode.WhenNull*` unmounts the focused control mid-edit** — backspacing a field to empty removes
   the element that has focus. (`EditControlBase.cs:260-264`) — see root cause A.
8. **Picker Clear button drops focus to `<body>`** and can strand an open `role="dialog"` plus its
   full-viewport backdrop, dismissable only by mouse. (`DatePicker.razor.cs:1242-1247`)
9. **No live region anywhere in `Select`** — filtering, "no results", selection, and tag removal are all
   silent. Every other announcing widget in the library ships this pattern (`Table.razor:34`), so this is
   inconsistent with the library's own convention, not a stance.
10. **Checked / indeterminate / selected states vanish in forced-colors mode** — all three are painted with
    `background-color` over an `opacity: 0` real input, so checked and unchecked render identically in HCM.
    (`edit-controls.css:260-293,485-496`)
11. **`autocomplete="one-time-code"` is the default for every non-password `EditString`** — a real autofill
    token reserved for OTP entry, applied to unannotated name/email/phone fields. Deliberate
    (README:2140) but conflicts with WCAG 1.3.5.
12. **The contrast-token cluster** — root cause B above.

`EditRadioString` renders an unlabeled radio for an empty-string option (RAD-1) · disabling the *selected*
radio can remove the whole group from the tab order (RAD-2) · required checked-list groups have no AT
signal, since the star is `aria-hidden` and `role="group"` forbids `aria-required` (LST-1) · empty

## Verified non-issues — do not spend effort here

These looked like defects and are not. Each was killed by measurement, not by assumption.

- **Target size (2.5.8) — 68 undersized elements, zero real failures.** Measured every focusable element on
  `/uikit`: 68 are under 24×24 (`wss-picker-clear` 14×14, `wss-alert-close` 12×12, table
  expand/filter 24×12, checkboxes 16×16). Computing the spacing exception properly — a 24px-diameter circle
  centred on each target must not intersect another's — **0 of 68 fail**. Any source-derived "target too
  small" claim must also fail spacing before it is actionable. (Two exceptions found by source review do
  fail spacing and are listed in Priority 3: CSS-8 and CSS-13.)
- **`LabelTooltip` does not poison accessible names.** Its `role="tooltip"` node sits *inside* the
  `<label>`, which would concatenate into every input's accessible name — but it computes `display: none`
  at rest, so the accname algorithm excludes it. The trigger is a real `<button aria-label="More
  information">`. Correctly built.
- **Validation/description wiring is sound — the thing most libraries get wrong.** 62 `aria-describedby`
  references on `/`, **0 dangling**. Every `error-msg-*` live region already exists in the DOM, empty, with
  `aria-live="polite"`, *before* any error occurs — so injected messages actually announce. A
  conditionally-rendered region would announce nothing.
- **`.edit-sr-only` is the correct recipe** (`clip-path: inset(50%)` + `border: 0`), with no
  `width:0`/`text-indent` anti-patterns in either stylesheet.
- **The `*/`-inside-a-comment landmine is absent** — comment delimiters balance exactly in both stylesheets
  (165/165 and 277/277).
- **`prefers-reduced-motion` coverage is complete** in `edit-controls.css` — all four motion declarations
  are covered.
- **Picker grid semantics are correct** — `role="grid"/"row"/"gridcell"`, per-day
  `aria-label="Sunday, February 1, 2026"` on the inner button, `aria-selected` on the committed cell, and
  roving `tabindex` (0 on selected, -1 elsewhere). Verified in the open state at runtime.
- **Select's open-state ARIA is correct** — `aria-activedescendant` resolves to a real `role="option"`,
  `aria-selected` present on *all* options (not just the selected one), disabled options handled
  consistently across every navigation path.
- **Page-level axe violations are demo-host, not library** — `document-title`, `landmark-one-main`,
  `page-has-heading-one`, `region` (41 nodes) all originate in the FormTesting host page. Likewise 28 of
  the 29 contrast violations on `/` are `wss-demo-nav-*` chrome; only one was library CSS.

## Regression check — the 2026-08-11 UI-kit remediation

Every finding the previous audit claimed fixed was re-verified against current source by content (not by
the now-stale line numbers). Result: **all HELD. No regressions, no partials, and no fix was found to have
introduced a new accessibility problem.**

Two points worth recording:

- The min-height sweep — the one item that audit's own "Correction" note flagged as having been *falsely*
  claimed fixed in its first wave — is now genuinely present across `wss-controls.css`.
- Items resolved "as documentation" were checked for the documentation actually existing. It does
  (README.md:321-323, 457, 472 and the `edit-controls` skill), so there are no phantom doc-fixes.

All four defects found by the runtime pass were confirmed as **NEW — never covered by the 2026-08-11
audit**, not regressions:

- The picker input role mismatch predates that remediation. Its M9 item flagged only the *missing*
  `aria-controls`, which the fix duly added — on top of an already-invalid role. So the fix made a
  pre-existing defect marginally worse (one more disallowed attribute on the same element) without being
  its cause. `Select.razor:39` already demonstrates the correct pattern the pickers never got.
- Weekday-header and table-empty-state contrast were never in scope: M9 discussed weekday headers purely
  structurally, and M11's CSS contrast list enumerates outside-month days and sort/filter icons but neither
  of these selectors.
- The nameless standalone `Select` was never discussed at all — the audit only ever considered the
  form-bound variants, which get their name from an external `<label for>`.

That last point generalises: **the previous audit's blind spot was the UI kit used *standalone*, outside a
form wrapper.** That is exactly the configuration an MFE consumer is most likely to reach for.

## Suggested remediation order

1. **Add axe to the e2e harness with a ratchet allow-list.** Without this, everything below can regress
   silently, and the next class of defect goes unnoticed the same way this one did.
2. **Priority 1 items 1–3** — they are the difference between a select/date field being usable with a
   screen reader and being unusable. Items 2 and 3 are small, local changes.
3. **Item 4 (focus visibility) + the forced-colors blocks** — one stylesheet change each, and `README.md`
   currently advertises high-contrast support that `edit-controls.css` does not implement.
4. **Item 5 (acronym labels)** — a single shared helper fix; note there are two independent
   implementations of the same broken rule.
5. **Root cause A (focus-to-`<body>`)** — one pattern applied at five sites; the library already has the
   helper.
6. **Root cause B (contrast token)** — correct the token, and correct the comments, so the next decision
   isn't made against bad arithmetic.

Nothing in this document has been changed in code; this pass was analysis only.
