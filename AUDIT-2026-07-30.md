# DRY & bug audit — 2026-07-30 (closed)

Working notes from a nine-area parallel audit of the `WssBlazorControls` library (post-10.7.0 audit wave).
Finding text and line numbers are preserved as originally written, against `master @ 011f2ca` — they are
**not** updated, so most no longer resolve. Read a finding as a description of the defect, and its outcome
line for what actually happened.

**Status:** CLOSED — all 73 findings are resolved. The audit ran across nine parallel areas (findings 1–43
the first six areas, 44–58 the Table/UiKit-picker wave, 59–73 the scalar-control wave), and the fixes then
landed in eight batches plus four rounds of regression hunting, `23a1eb3..b9d42ae` (~70 commits, all on
`master`, all against the unreleased `10.7.0`). Batch 1 (findings 59–66) landed directly; batches 2–8 came
in through merge commits `66fafb5`, `31f5026`, `8cbeb94`, `b9d42ae`, `5a8eb08`, `d922a21`, `d361b8d`, each
naming its finding numbers.

Every finding below carries an **Outcome** line naming the commit(s) that closed it. Four closed differently
than the finding proposed — **6** (fixed with a documented limitation, cleaner redesign deferred), **22**
(unified on one behavior, no new API), **26** (already correct; documented only), **29** (half deliberately
reverted) — so read the outcome, not the proposal.

**The most valuable part of this document for a future reader is the [Regression hunt](#regression-hunt--defects-the-fix-batches-themselves-introduced-or-left-half-done)
section at the end**: 19 defects that the fix batches *created or left half-done*, and the fix shapes that
keep producing them in this codebase.

Legend: **[V]** = independently re-verified against the source by the orchestrator; **[A]** = agent-reported with quoted evidence, not independently re-read.

## Bugs — medium

1. **[V] `[Range(0, …)]` misclassified by validation-message rewrite** — `Controls/Helpers/ValidationHelper.cs:105-110, 176-190`
   `IsTypeMinSentinel` treats `"0"` as a type-min sentinel (`byte`/`uint`/`ulong`/`ushort.MinValue.ToString()` are all `"0"`).
   - `[Range(0, int.MaxValue)]` (the ubiquitous "non-negative" idiom): both bounds read as sentinels → no rewrite branch matches → raw framework text with `2147483647` shown verbatim — the exact case the rewrite exists to suppress.
   - `[Range(0, 100)]`: min "0" sentinel, max isn't → rewritten to "Cannot exceed 100", hiding the real lower bound.
   Note: `AttributesHelper.IsRangeSentinel` deliberately excludes 0 for DOM rendering — the message layer contradicts it.
   **Outcome — FIXED** in `4646115` (drop `"0"` from the min sentinels), then superseded by `96349c6`, which
   replaced both layers' private lists with one shared `RangeSentinels` predicate. See the regression-hunt
   section: `4646115` alone still left the two layers disagreeing on 8 of 12 type extremes. One residual
   remains open — see [Still open](#still-open-follow-ups) (a).

2. **[V] `EditDateRange` parse-error store never follows an `EditContext` swap** — `Controls/EditDateRange.razor.cs:486, 503-516` vs swap handling at `:439-455`
   `_parseErrorMessages ??= new ValidationMessageStore(EditContext)` binds once to the first context. The control explicitly supports context swaps (re-derives both FieldIdentifiers) but never rebinds/clears the store. After a form reset, a new parse error is written to the dead context → no message renders, `aria-invalid` stays off, bad text silently reverted with zero feedback. (`EditDate`'s twin block is safe only because `InputBase` throws on context swap — divergence exactly where the extra capability needed the store to follow.)
   **Outcome — FIXED** in `410da43`: `OnParametersSet` clears the old store and drops it to null on a genuine
   swap, so the next parse error lazily rebinds against the current context. The base's subscribed context was
   exposed (later as `ValidationStateSubscription.SubscribedEditContext`, `56c1cf6`) so the swap can be detected.

3. **[V] Select: `RebuildFiltered` clamps `_activeIndex` to bounds, not to a selectable row** — `Controls/Select/Select.razor.cs:494-497`; entry paths `:253-265, 681-682, 742-743, 784-785`
   Rebuilds not going through `ApplySearchAsync`/`SetInitialActive` (Options reassigned while open; multi-mode select/clear/tag-commit clearing search text) can land the active index on a group header or disabled option → highlight and `aria-activedescendant` vanish, Enter goes dead (or in Tags mode commits a spurious new tag). `ActiveOption`'s own comment asserts this "is never supposed to happen".
   **Outcome — FIXED** in `046ff21` (`ClampActiveToSelectableRow` + shared `FindSelectableFrom`), corrected in
   `1abebf4`: the first fix still fell back to raw index 0 when *nothing* was selectable, which on an
   all-disabled list is a disabled option. Both settle paths now go to `-1`.

4. **[V] Select: tag-remove × and clear button drop keyboard focus to `<body>`** — `Controls/Select/Select.razor.cs:694-700` (`RemoveAsync`), `:718-744` (`ClearAsync`); buttons in `Select.razor:84-91, 117-119`
   Both delete the focused button from the DOM without restoring focus (contrast multi-`SelectAsync:684` and `CommitTagAsync:786`, which end with `FocusInputAsync()`). Keyboard user activates × → focus falls to `<body>`, Tab restarts at page top, open dropdown stays open with focus outside (no focusout fires on element removal, so focus-out dismiss doesn't run).
   **Outcome — FIXED** in `046ff21` (both paths end with `FocusInputAsync`), narrowed in `9cf7808`:
   `RemoveAsync` now takes an explicit `restoreFocus` flag, because the Backspace tag-remove path never lost
   focus and the blanket refocus cost one circuit round-trip per keystroke on Blazor Server.

5. **[V] `CheckboxOptionList` crashes on duplicate option values** — `Controls/CheckboxOptionList.razor:11`
   `@key="option"` keys siblings on the option value. Alias enum members (`Active = 1, Enabled = 1`) or duplicate strings in `EditCheckedStringList.Options` → duplicate `@key` → Blazor throws `InvalidOperationException` on first re-render (first render succeeds; first click crashes). The id machinery (`ToUniqueIds`) was hardened for colliding options; radio/select siblings (no `@key`) survive the same input — only the checkbox list hard-crashes.
   **Outcome — FIXED** in `2413c47`: keyed on the already-unique id from `EnumHelpers.ToUniqueIds` instead of the option value.

6. **[V] Tabs: conditional tab inserted before parameter-skipped siblings renders in the wrong position permanently** — `Controls/UiKit/Tabs.razor.cs:85-106` (`StartCollectingTabs` straggler merge)
   Stragglers (content-less tabs whose primitive params were unchanged, so Blazor skipped `SetParametersAsync`) are re-inserted at their **old** `_tabs` index. Declared `[d(new), a, b, c]` promotes as `[a, b, c, d]` and no later pass corrects it (skipped tabs never re-register). Mechanism only correct for appends/removals; tests cover removal/disable, not insertion-before-skipped-siblings.
   **Outcome — FIXED WITH A DOCUMENTED LIMITATION** in `c5cab30` (a generation `@key` on the `ChildContent`
   `CascadingValue` forces one clean re-registration pass in document order), repaired in `1a9695e` (the
   rebuild had destroyed every tab's `ButtonRef` and broken arrow-key navigation), bounds pinned in `eee7ac1`.
   **Limitation:** the rebuild replaces the whole `ChildContent` subtree, so a *non-`Tab`* component a consumer
   declared inside `<Tabs>` is torn down with it and loses instance state. It happens only on a structural
   insertion before parameter-skipped siblings, never on an ordinary re-render or a removal, and is documented
   on `Tabs.ChildContent`. A cleaner redesign — having `Tab` render its own nav button, which removes the
   registration-ordering problem entirely — was identified and **deliberately deferred** as a separate design
   change; see [Still open](#still-open-follow-ups) (c).

7. **[V] `ToastQueue`: `Clear()`/`Dispose()` races timer expiry → `ObjectDisposedException`** — `Controls/UiKit/ToastQueue.cs:94-111`
   `CancelAllTimers` iterates a `Values` snapshot without claiming ownership (`CancelTimer` uses exclusive `TryRemove`). A toast expiring on a threadpool thread and a concurrent `Clear()` can both reach the same CTS; one side `Cancel()`s a CTS the other already disposed → ODE out of the user's `Clear()` (circuit error on Server) or a faulted fire-and-forget task. Fix shape: `CancelAllTimers` claims each entry via `TryRemove` per key.
   **Outcome — FIXED** in `7a595a3`, exactly the proposed shape (per-key exclusive `TryRemove` claim).

8. **[A] Wasm toast statics enforce WASM-only by docs alone — silent cross-user leak on Server** — `Controls/UiKit/WasmMessageContainer.razor:5-12`, `WasmNotificationContainer.razor:5-18`, `Wasm*Service.cs:16`
   A Server app using `<WasmNotificationContainer />` compiles and works in single-user dev; in production the process-static service is shared across every circuit → user A's notification renders on user B's screen. Suggested: fail-fast assert (`OperatingSystem.IsBrowser()`) in `OnAfterRender(firstRender)` (prerender-safe; `OnInitialized` would false-positive during server prerender of a WASM app).
   **Outcome — FIXED, then corrected twice.** `d100fa9` added the proposed `OperatingSystem.IsBrowser()`
   assert; `d3613a5` replaced it with `RendererInfo.Name == "Server"` (the `IsBrowser()` test also rejected
   Blazor Hybrid/MAUI, which serves one user per process and is therefore *safe* for a process static);
   `f464ce9` gated the demo gallery's own `Wasm*Container` usage on the same condition, since the new throw
   took `<UiKitGallery />` down on Server. Net rule: **refused on Blazor Server (and InteractiveAuto's server
   phase); permitted on WebAssembly, WebView/Hybrid, and the static prerender pass.**

9. **[V] CSS: RTL stragglers — pagination + picker `<select>`s pair physical padding with a logical arrow** — `wwwroot/wss-controls.css:1511/1522-1525` and `:3080/3091-3094`
   `padding: 0 28px 0 8px` (physical) + `inset-inline-end: 8px` arrow → in RTL the arrow flips to the left over the option text, 28px dead space on the right. Should be `padding-inline: 8px 28px`. Not in the file's documented "deliberately physical" exception list.
   **Outcome — FIXED** in `239a3cf` (`padding-inline`/`padding-block` on both selectors; LTR pixel-identical).

10. **[A] CSS: `[data-tooltip]` hover tooltip missing from the reduced-motion block** — `wss-controls.css:1095, 1120` vs block at `:3766-3817`
    The UI-kit hover tooltip keeps its slide/scale transition under `prefers-reduced-motion` while `edit-controls.css`'s tooltip suppresses its own "mirroring wss-controls.css" (WCAG 2.3.3 gap). Addendum: `.wss-table-expand-btn` color transition (`:2153`) also absent.
    **Outcome — FIXED** in `239a3cf` (both the tooltip arrow/body transitions and the expand-button color transition added to the reduced-motion block).

## Bugs — low

11. **[V] ARIA state resolved against stale `FieldIdentifier` on context swap** — `Controls/EditControlListBase.cs:207-221` and `Controls/EditDateRange.razor.cs:439-455` (same shared-base ordering)
    `RefreshAriaState()` runs before `SyncFieldRegistration` replaces the FieldIdentifier(s), so on a model/context swap `aria-required` / the star resolve via `FormOptions.RequiredResolver` against the dead model and stay stale until some later parameter cycle. (Found independently by two agents.)
    **Outcome — FIXED** in `62d1000`: the ARIA refresh moved to the end of `OnParametersSet` in both classes.
    `EditDateRange`'s parse-error-store clear deliberately stays first — that one has to see the *old* context.
    This ordering (registration first, ARIA refresh last) is now a convention; recorded in the skill's `architecture.md`.

12. **[V] `FormOptions.FieldIds` last-writer-wins never restored on unregister** — `Controls/FormOptions.cs:33-34, 52-62`
    Two controls bound to one property (page + modal, modal registers last with `IdPrefix`): modal disposes → owner set keeps the shared entry alive but `FieldIds` still holds the modal's DOM id → `ValidationView` anchors `href="#modal-Name"` to a removed element.
    **Outcome — FIXED** in `b93ce1c`: the owner set carries each owner's registered id, so the last remaining registrant's id is restored on unregister.

13. **[V] Failed init leaves `default(FieldIdentifier)` that `Dispose` then hashes** — `Controls/EditControlBase.cs:112-113, 166-171`; `EditControlListBase.cs:124-125, 225-229`
    Missing `@bind-Value` → `OnInitialized` throws the helpful message before `InitState` runs → `Dispose` calls `UnregisterField(default)` → `FieldIdentifier.GetHashCode` hashes a null `FieldName` → `ArgumentNullException` from disposal masks the real diagnostic (needs a cascaded `FormOptions`).
    **Outcome — FIXED** in `c783d53`: both roots only unregister once `InitState` has completed.

14. **[A] Sentinel-twin drift: float-as-double literal only on the min side** — `ValidationHelper.cs:182 vs 184-190`
    `IsTypeMinSentinel` has `"-3.4028234663852886E+38"`; `IsTypeMaxSentinel` lacks the positive counterpart → `[Range(-100f, float.MaxValue)]` shows the raw huge max while the mirrored min case rewrites correctly.
    **Outcome — FIXED** in `4646115` (added the positive counterpart), then `fc082af` (both float sentinels are
    computed at call time instead of frozen as an invariant-format literal — the literal matched nothing under a
    `,`-decimal culture, so the whole rewrite failed under de-DE), then folded into `RangeSentinels` by `96349c6`.

15. **[A] `ValidationHelper` message punctuation drift** — `ValidationHelper.cs:46-47`
    Unlabeled `MaxLengthList` ends with a period; its labeled twin and every neighboring message do not.
    **Outcome — FIXED** in `4646115` (trailing period dropped).

16. **[A] `EditDateRange` min/max "union" is actually first-non-null** — `EditDateRange.razor.cs:395-396` (contradicts comment at `:387-394`)
    Conflicting per-field date bounds → shared calendar blocks values one field's own validation accepts. True union needs min-of-mins / max-of-maxes.
    **Outcome — FIXED** in `410da43` (min-of-mins / max-of-maxes), documented in `7b665c5`. The code comment had
    overclaimed in the other direction: one calendar has one min and one max, so the result is the convex **hull**,
    not the union — disjoint per-field `[Range]`s leave the gap selectable. That limitation is now stated in the
    code comment, the test-class doc, the README and the skill.

17. **[A] `EditDate<DateTimeOffset>` write-back can throw circuit-killing `ArgumentOutOfRangeException`** — `EditDate.razor.cs:393-397`
    `new DateTimeOffset(value)` unguarded; typed year-1 date in an east-of-UTC zone puts the UTC instant below `DateTimeOffset.MinValue`. The comment acknowledges the throw but doesn't guard it.
    **Outcome — FIXED** in `8c82f3b`: new `TryToDateTimeOffset` performs the constructor's own bounds check and

18. **[A] Gregorian-forcing gaps in read-only date rendering** — `EditDate.razor.cs:456` (FormatException fallback uses bare `ToString()` → CurrentCulture; EditDateRange's twin at `:578` passes the Gregorian culture) and `EditDateNative.razor.cs:175-178` (read-only formats with raw `CultureInfo.CurrentCulture`; EditDate forces Gregorian) → under th-TH the two "interchangeable" controls disagree by 543 years.

19. **[A] Select `DefaultOpen` bypasses `SetInitialActive`** — `Select.razor.cs:232-235` vs `:548-556`

20. **[A] Select multi/clear paths don't cancel the in-flight debounce** — `Select.razor.cs:669-685, 718-744` (only `CloseAsync:584-586` cancels)

    **Outcome — FIXED** in `046ff21`: the new shared `ResetSearch` helper cancels the debounce on all four paths.

21. **[A] `SelectOptionList` option ids not de-duplicated** — `Controls/SelectOptionList.razor:14, 38, 47-48`

## DRY

31. `ValidationView` hand-rolls the subscription sync that was just centralized as `SyncValidationSubscription`/`DetachValidationSubscription` — third live copy (`ValidationView.razor:40-68` vs `EditControlParametersBase.cs:73-97`).
    **Outcome — FIXED** in `56c1cf6`: mechanics extracted to a standalone `ValidationStateSubscription` helper that both drive (`ValidationView` shares none of the controls' parameter surface, so inheriting the base was not an option). The base's `_subscribedEditContext` field became the `SubscribedEditContext` property `EditDateRange` reads before a swap.

32. `EditControlBase` ↔ `EditControlListBase` mirror far more than the acknowledged one-line forwards: full 12-param `IEditControl` block + 3 cascading params (redeclared incl. `IsEditMode = true` default), 6 derived-state fields, `OnInitialized`/`InitState`, `RefreshAriaState`, `IsRequiredResolved`, `ShowEditor`/`ShouldHideLabel`. Finding 11 is live drift of exactly this class. `InputBase` constraint prevents a shared ancestor, but more could sit in `EditControlInit`.
    **Outcome — FIXED (as far as the `InputBase` constraint allows)** in `5f0f614`: `EditControlInit` gained `InitAndRegister`, `RequireBinding`, and an `IEditControl` overload of `ResolveAriaState`. The parallel `[Parameter]` declarations necessarily stay — Blazor requires a settable property per component type.

33. `EditDateRange` lacks the `Size` parameter `EditDate`/`DateRangePicker` have (`EditDate.razor.cs:94`, `DateRangePicker.razor.cs:185`) — **and** a consumer's `Size="Small"` lands in `AdditionalAttributes`, splats onto the picker's `SelectSize` parameter as a string → runtime cast exception. Parity gap with a footgun. **[V]**
    **Outcome — FIXED** in `410da43` (`EditDateRange.Size`, `SelectSize`, forwarded to the inner picker); documented in `7b665c5`, which found it had shipped with no documentation anywhere.

34. `IsValueDefault()` boxed date-type switch duplicated char-for-char (`EditDate.razor.cs:463-470`, `EditDateNative.razor.cs:191-198`, variant `EditDateRange.razor.cs:351`).
    **Outcome — FIXED** in `410da43` + `8c82f3b`: hoisted to `EditControlInit.IsDateValueDefault`, adopted by all three.

35. `PickerAttributes` splat-builder near-duplicate (`EditDate.razor.cs:415-429`, `EditDateRange.razor.cs:531-543`, differ only in class source).
    **Outcome — FIXED, but not when first reported.** `410da43`'s commit message (and the test comment it added)
    claimed the builder had been hoisted into `EditControlInit.BuildPickerAttributes` and shared —
    **it had not**: `EditDateRange` kept its inline copy and `EditDate` was the helper's only caller. The hoist
    was actually completed in `2b101d8`, which also corrected the misleading test comment. No behavioral gap
    existed in the interim (the inline `FieldCssClass is not null` and the helper's `IsNullOrEmpty` guard are
    equivalent), so this was an audit-trail correction, not a bug fix.

36. ~20 pass-through parameters + `EffectivePlaceholder` + `SelectLabelCache` wiring duplicated verbatim between `EditSelectSearch` and `EditMultiSelect` (both `.razor.cs:20-104`, markup 12-43/20-54); "Please select" literal lives in 3 places.
    **Outcome — PARTIALLY FIXED (by design)** in `478bb7d`: every literal default (`"Please select"`, `"No data"`,
    `"Remove {0}"`, the clear labels, `"Options"`) and the placeholder resolution chain moved to a new
    `SelectDefaults`. The ~20 parameter **declarations** cannot be hoisted — `EditSelectSearch` is an `InputBase`
    and `EditMultiSelect` a plain `ComponentBase`, so no shared ancestor below `ComponentBase` exists, and a
    Blazor parameter must be a settable property on the component type itself. That constraint is now recorded
    in `SelectDefaults`' remarks and on both wrappers.

37. `Select.razor.cs`: `_searchText = ""; RebuildFiltered();` ×4 and `ValuesChanged.InvokeAsync(_selected.ToList())` ×4 — the copies' differing side effects *are* findings 3 and 20.
    **Outcome — FIXED** in `046ff21`: `ResetSearch` and `RaiseValuesChangedAsync` replace all eight copies.

38. `wss-select.js placeDropdown` vs `wss-overlay.js placePanel` — same ~15-line orchestration, parameterizable (placePanel's own comment concedes it).
    **Outcome — FIXED** in `aad5231`: both are now thin wrappers over `wss-overlay.js`'s `placeAnchoredPanel`, supplying the three knobs that actually differ. Exported names/signatures/return contracts unchanged; equivalence verified by running both revisions over 33,600 geometry combinations.

39. `EditSelect` ↔ `EditSelectString`: three byte-equivalent overrides (`TryParseValueFromString`/`FormatValueAsString`/`IsValueDefault`), coupling acknowledged in comments but unenforced (`EditSelect.razor.cs:34-50`, `EditSelectString.razor.cs:56-66`).

59. **[V — empirically confirmed] `EditString.SafeUrl` allow-list bypassable with a tab/CR/LF inside the scheme → `javascript:` executes** — `Controls/EditString.razor.cs:93-103`, rendered into `href` at `EditString.razor:75`
    ```csharp
    if (Uri.TryCreate(Url, UriKind.Absolute, out var uri))
        return uri.Scheme is "http" or "https" or "mailto" ? Url : null;
    return Url;   // anything Uri can't parse is treated as a safe relative URL
    ```
    Confirmed by running the cases against .NET 10.0.5 (`Uri.TryCreate`, `UriKind.Absolute`):

    | input | TryCreate | `SafeUrl` result |
    |---|---|---|
    | `javascript:alert(1)` | true | blocked ✓ |
    | `" javascript:alert(1)"` (leading space) | true | blocked ✓ |
    | `java<TAB>script:alert(1)` | **false** | **returned verbatim** |
    | `javascript<TAB>:alert(1)` | **false** | **returned verbatim** |
    | `java<LF>script:alert(1)` | **false** | **returned verbatim** |
    | `java<CR>script:alert(1)` | **false** | **returned verbatim** |

    The WHATWG URL basic parser removes all ASCII tab/newline from input before parsing, so the browser
    re-forms `javascript:alert(1)` from the `href` and runs it on click. `Url` is documented as bindable
    from model data, so any stored/user-supplied value reaches this. Fix: strip or reject `\t\r\n`
    before the `TryCreate` check (stripping matches browser behavior, so the scheme check then sees
    what the browser will see). Worth a bUnit test per case above.
    **Outcome — FIXED** in `6534dda` (strip ASCII tab/CR/LF first, and render the stripped value rather than the
    raw one), completed in `f228a65`: the first fix **missed the WHATWG parser's separate, earlier step** —
    trimming leading/trailing C0 control (U+0000–U+001F) or space. A leading `U+0001` isn't a valid scheme-start
    character, so `Uri.TryCreate` still failed and the "unparseable means safe relative URL" branch returned the
    raw value. `SafeUrl` now performs **both** preprocessing steps in the browser's order. U+007F (DEL) is
    deliberately left untrimmed — it isn't in WHATWG's "C0 control or space" set, so browsers don't trim it
    either, and it fails to parse identically in both parsers. bUnit theory extended with the confirmed bypass
    cases plus `data:`/`vbscript:` variants.

- Pickers: `WeekStart`/`WeekEnd` year-1/9999 clamps, `TryParseWeekShorthand` boundary walk + year-9999 overflow catch, quarter/decade clamps, `YearRange` [1,9999] clamp matched by both `OnYearSelectChanged` clamps, never-jump step/disabled composition in `PickerTimeRow`, typed-input revert rendering, preset guard/swap ordering, `_pendingInputFocus` staleness, JS interop degrade paths.

## Regression hunt — defects the fix batches themselves introduced or left half-done

After the eight fix batches, four rounds of regression hunting were run against the *fixes*, not the original
code. They found **19 defects that the fixes created or left incomplete** — several of them worse than the
finding being closed. This section is the most transferable part of the document: the recurring fix shapes
below keep producing defects in this codebase, so treat them as review checklists.

### Shape 1 — "I matched the spec's first preprocessing step" (security/parsing)

- **`f228a65` — the `javascript:` URL fix (finding 59) missed leading C0 control bytes.** `6534dda` stripped
  ASCII tab/CR/LF, matching one WHATWG step, and stopped. The parser has an *earlier* step: trim
  leading/trailing C0-control-or-space. `"\u0001javascript:alert(1)"` still failed `Uri.TryCreate`, still fell
  into the "unparseable means safe relative" branch, and the browser trimmed the byte itself and ran the script.
  **Lesson: when mirroring an external parser, enumerate every preprocessing step and its order — a partial
  mirror is a live bypass, not a partial fix.**
- **`96349c6` — the sentinel predicates still disagreed on 8 of 12 type extremes.** Finding 1's fix (`4646115`)
  corrected `ValidationHelper`'s list, but `AttributesHelper` kept its own separate list. `[Range(1, 255)]` on an
  `int` still rendered `max="255"` while the message said only "Must be at least 1"; `[Range(-32768, 100)]`
  rendered `min="-32768"` while the message claimed no floor. Both layers now share one `RangeSentinels` table,
  side-aware, with a regression theory over every numeric type extreme (8 of its cases failed before the change).
  **Lesson: fixing one of two hand-synced tables leaves the inconsistency the finding was actually about.**
- **`fc082af` — the float sentinel was the one candidate frozen as an invariant-format literal.**
  `RangeAttribute` formats under the *validation-time* culture, so `"3.4028234663852886E+38"` matched nothing
  under de-DE and the rewrite failed exactly where it was needed.

### Shape 2 — "the rebuild is free" (render-tree surgery)

- **`1a9695e` — the Tabs ordering fix (finding 6) destroyed every tab's element reference and broke keyboard
  navigation.** `c5cab30`'s generation `@key` rebuilds the `Tab` children, but the nav `<button>`s live in `Tabs`'
  own render tree, *outside* the keyed subtree. Blazor only re-runs an `@ref` capture for an element it
  **creates**, so the retained, unkeyed buttons left every fresh `Tab` holding `default(ElementReference)`:
  arrow-key `FocusAsync` threw into a bare `catch`, DOM focus never moved, and the roving `tabindex` pointed at
  a button the browser had not focused. Fixed by `@key`-ing the nav button by its `Tab` (which also closes a
  latent reorder hazard) and narrowing the swallowing `catch` to the three failures it can tolerate.
- **`eee7ac1` — the rebuild's blast radius was unbounded and undocumented.** A test now pins that an ordinary
  re-render and a tab removal never rebuild, and the consumer-facing limitation is stated on `Tabs.ChildContent`.
  **Lesson: a `@key` bump is a teardown. Enumerate everything in and around the keyed subtree that holds
  identity — element references, subscriptions, timers, caches — before reaching for one.**
- **`e56022c` — extracting shared internals (findings 57, 58) put four new public components on the NuGet
  surface.** Razor compiles every component to a `public` class, so `PickerMonthHeader`, `PickerWeekdayHeader`,
  `PickerTimeRowSlot` and `PickerTimeRow` all shipped as standalone-constructible types. `PickerTimeRowSlot`
  NRE'd on its first `Picker.TimeRowHour` read when `Picker` was unset (`[EditorRequired]` is a tooling hint,
  not a runtime check), and `PickerMonthHeader` rendered a degenerate header with no selectable month. All four
  now render nothing rather than taking a consumer's app down.

### Shape 3 — "promote the helper" (semantics smuggled in a refactor)

- **`ffacc90` — promoting `NonZero` (finding 70) turned EditFile's negative bounds into total upload rejection.**
  The original was `attrValue > 0 ? attrValue : default`; `NonZero` treats only 0 as the sentinel. A consumer
  writing the widespread `[FileConstraints(MaxFileSizeBytes = -1)]` "unlimited" convention got a literal cap of
  −1, which rejects every file (`size >= 0` is never `<= -1`), instead of the 10 MB default. A separate
  `AttributesHelper.Positive` was added; both helpers now document which sentinel convention they implement.
  **Lesson: a "shared helper" is a behavioral contract. Diff the predicate, not just the call sites.**
- **`2b101d8` — finding 35's hoist had never actually happened.** `410da43`'s commit message and the test
  comment it added both asserted `BuildPickerAttributes` was hoisted and shared with `EditDate`; `EditDateRange`
  kept its inline copy and `EditDate` was the helper's only caller. Harmless behaviorally, but the audit trail
  was false for four batches. **Lesson: a commit message is not evidence; the assertion has to be in a test.**

### Shape 4 — "guard every commit path" (claims of exhaustiveness)

- **`10a5fb1` — the picker's "every commit path guarded" work (finding 47) left the time selects unguarded.**
  `ApplyTimePartAsync` checked only `IsTimeDisabledForCommit` — the *time half* of the dispatcher — so the
  hour/minute/second selects were the one route that committed a **date** nothing had validated. With `Min` a
  month out, the day button and the Now link both rendered disabled and the typed path rejected, while changing
  the hour fired `ValueChanged` with today (`ComposeTimePart` falls back to `DateTime.Today`). Also: the
  day-click guard tested the raw composition rather than the **normalized** value actually committed.
- **`610d8f9` — the same, doubled, in `DateRangePicker`'s session, plus a silent OK.** Four defects: the time
  selects used only the time half; **a rejected OK returned bare** — no `disabled`, no `aria-disabled`, no close,
  no advance, no callback, no feedback whatsoever; the pre-advance guard judged the pre-swap value against the
  endpoint it was about to leave; and the pending-state write sat ahead of the guard's `return`, so a rejected
  OK still mutated. **Lesson: "every path is guarded" needs a path inventory, and a guard that only prevents
  must also be visible — a rejection with no UI signal is its own bug.**

### Shape 5 — "restore the invariant" (fallbacks that land on the illegal state)

- **`1abebf4` — the Select highlight fix (finding 3) pinned the highlight to a disabled option.** Both settle
  paths fell back to raw index 0 when nothing was selectable, which on an all-disabled list *is* a disabled
  option — the exact opposite of `ClampActiveToSelectableRow`'s stated contract.
  `aria-activedescendant` pointed at an `aria-disabled="true"` row while Enter did nothing. Both settle on `-1`
  now, after verifying every `-1` consumer.
- **`1be5b5e` — the filter prune cleared `FilterApplied`/`FilterPending` but not `FilterOpen`**, and returned
  early when nothing was selected. An open, untouched dropdown left the flag stuck true forever, which pinned
  `Table.AnyColumnFilterOpen` true for the table's lifetime (every other column's filter then skipped its focus
  restore and dropped focus to `<body>`) and made the dropdown reappear already open, its invisible full-screen
  backdrop swallowing the next click.
- **`9cf7808` — the Select focus-restore fix (finding 4) added a circuit round-trip per keystroke.** The
  refocus is only needed on the × button path (the focused element is removed from the DOM); the Backspace
  tag-remove path never loses focus, so holding Backspace to clear 20 tags issued 20 interop calls where the
  same gesture previously issued zero.

### Shape 6 — "compare the parameter" (reference vs. value vs. identity)

- **`ffacc90` — `FilterOptions` was snapshotted by reference, so `OptionsEqual`'s `ReferenceEquals` fast path
  compared the consumer's list to itself.** A consumer refilling one `List<TableFilterOption>` field in place
  (`Clear()` + `AddRange`, the ordinary data-derived shape) never tripped the prune, so finding 45's fix did
  nothing for them.
- **`b53172b` — `Property`/`OnFilter`/`SortBy` were left out of the column snapshot** on the reasoning that a
  lambda closes over current parent state. True for output, false when the parent **selects a different
  delegate**: a swapped `Property` rendered the old property forever, a swapped `OnFilter`/`SortBy` left the
  cached `_filtered`/`_sorted` in place while a filter/sort was active. They are compared by **method identity**,
  not instance — an instance compare would loop, since a markup lambda capturing a local is a fresh object each
  pass. **Lesson: for delegates, pick the comparison deliberately (reference loops, identity works); for
  collections, reference comparison is almost always wrong.**

### Shape 7 — "fail fast" (guards that ask the wrong question, or break a working host)

- **`d3613a5` — the Wasm-toast guard (finding 8) rejected Blazor Hybrid.** `!OperatingSystem.IsBrowser()` also
  catches MAUI/WPF/WinForms `BlazorWebView`, where `IsBrowser()` is false yet one process serves exactly one
  user — the very condition that makes a process-static toast store *safe*. The guard now asks
  `RendererInfo.Name == "Server"`, which permits WebAssembly, WebView and the static prerender pass and still
  catches InteractiveAuto's server phase.
- **`f464ce9` — the new throw took the published demo gallery down on Server.** `UiKitGallery` embeds
  `<WasmMessageContainer />`/`<WasmNotificationContainer />` unconditionally, and `WssBlazorControls.Demo` is a
  published package — a consumer dropping `<UiKitGallery />` on a Server page got an unrecoverable exception
  where it used to degrade. The toast section is now gated on the same condition the containers check.
  **Lesson: adding a throw is an API break for every existing call site, including this repo's own.**

### Shape 8 — "that's the last one" / "unify the token"

- **`fe05e8b` — the Table localization sweep (finding 50) wasn't the last hardcoded English.** `87e29a0`'s
  message claimed it had removed the last hardcoded strings; three `Pagination*` aria-labels and the sort
  button's `"Sort"` fallback were still unreachable. (And one still is — see [Still open](#still-open-follow-ups) (b).)
- **`2e71fd9` — the `--color-danger` unification (finding 29) silently reverted a WCAG decision.** `2fafe42`
  unified `--edit-color-danger`'s fallback to `#ff4d4f` — dropping validation-message text from ~5.9:1 to 3.27:1
  on white, below WCAG 1.4.3's 4.5:1. The divergence was deliberate and already documented at the declaration
  site (text needs 4.5:1; chrome/borders need only 3:1 under 1.4.11). Reverted, with a cross-reference comment
  added on `--wss-color-error`. **Lesson: before "unifying" two values, read the comment at each declaration —
  a documented divergence is not drift.**
- **`bce01da` — the unified Other-radio behavior (finding 22) held preserved text too long.** An empty
  `OtherValue` arriving while Other is still the selected option is a genuine parent-side clear (form reset,
  reload), not the empty the control writes itself on a switch-away; the preserved copy is now dropped so
  nothing stale is re-committed.

## Still open (follow-ups)

Deliberately not closed in this wave. Recorded so they aren't lost.

a. **`[Range(int.MinValue, int.MaxValue)]` (both bounds sentinels) still falls through to the raw framework
   message.** `ValidationHelper.GetValidationMessage`'s numeric-range branch rewrites only the one-sided
   (`min` sentinel XOR `max` sentinel) and neither-sentinel cases; when *both* bounds are sentinels no branch
   matches and `return message` hands back the framework's own text with the extremes spelled out — the exact
   case the rewrite exists to suppress. Finding 1's original bullet called this out and it survived both
   `4646115` and `96349c6`. A "no bounds at all" message (or falling back to the type-name message) would close it.

b. **`TableColumnFilter`'s headerless-column fallback string is still hardcoded.**
   `TableColumnFilter.razor:106` — `string.IsNullOrEmpty(Column.HeaderText) ? "Filter" : string.Format(FilterButtonLabelFormat, Column.HeaderText)`.
   Every neighboring string has an override parameter (`FilterButtonLabelFormat`/`FilterResetLabel`/`FilterOkLabel`,
   and now `SortLabel` for the exactly-parallel sort case); this one has none, so a localized table announces a
   headerless column's filter button in English. Mirror `SortLabel`: add a `FilterLabel` parameter on `Table`,
   forwarded to the filter component.

c. **The `Tabs` redesign (finding 6).** Having each `Tab` render its own nav button removes the
   registration-ordering problem at the root, which retires both the straggler-merge heuristic and the
   generation-`@key` rebuild — and with it the documented `ChildContent` teardown limitation and the
   `@key`-the-nav-button repair. Deliberately deferred as a separate design change rather than folded into a
   bug-fix batch.

d. **No RTL or forced-`prefers-reduced-motion` e2e coverage exists.** Findings 9, 10, 27 and 28 were all
   verified by reading CSS and reasoning about computed values. Playwright can set both (`dir="rtl"` on the
   demo host root; `reducedMotion: "reduce"` in the browser context / `Page.EmulateMediaAsync`), so a small
   pair of suites — one RTL pass over the pagination/picker selects and the tooltip offsets, one
   reduced-motion pass asserting `transition-duration: 0s` on the newly covered selectors — would turn four
   reasoned fixes into pinned ones. Nothing today would catch a regression in any of them.
